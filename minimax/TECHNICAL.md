# 一页技术说明

当前为保存进度版本：数据库和状态模块已验证，MiniMax 请求因余额不足失败，完整模型改码流程待执行。下文说明实现设计，不表示六项验收已通过。

**目标**：面对明确的业务演进任务，将有效规格、实际代码和验证测试组合为可追溯上下文，再由 MiniMax 修改业务代码，并保存可恢复的验证进度。

**数据路径**：工程文件 → 规范化文档/AST 符号 → seekdb `minimax_sdd_materials` → 参数化全文查询 → 带来源上下文 → MiniMax 最终代码 → 不变测试 → PowerContext 任务记忆 → 独立进程恢复后的下一步上下文。

| 模块 | 实际职责 |
|---|---|
| `documents.py` | 扫描规格、Python 代码和测试；保留全文、相对路径、SHA-256、行号和函数/类名；拒绝越界和过大输入 |
| `database.py` | 通过 PowerContext 的 SeekDBProfile 打开真正嵌入式 seekdb；建表与全文索引，按项目事务导入、修订、删除；对三类来源分别全文查询并记录实际返回值 |
| `context.py` | 根据任务查询选择规格、代码和测试，校验文件与索引版本；把真实 PowerContext 任务进度纳入输出；版本变化标记需要重新验证 |
| `minimax_client.py` | 向官方 MiniMax OpenAI 兼容端点提供上下文；保存最终输出和调用元数据；解析受约束代码修改，校验来源哈希，生成前后快照和 diff |
| `state.py` | 使用 PowerContext Memory 的 remember/revise/list 与稳定 scope 保存任务已完成项、待办、测试结果、版本及模型响应 ID；实际打开持久化数据库恢复 |
| `workflow.py` / `cli.py` | 从空目录初始化，执行同一组修改前后测试；跨进程重新打开模块并使用恢复结果；重新导入新规格，输出机器可读验收记录 |

**上下文选择**：以任务 query 为检索输入，对规格、代码和测试分别取最多三份匹配文档；内容直接来自 SQL 返回的 `source_text`，同时携带数据库修订号及来源位置。分组取回避免代码命中挤掉规格或回归测试。没有需要的类别或发现陈旧来源时明确失败。样例明确声明四份必要来源，并在初始化时核验。

**技术分工**：MiniMax 实际生成业务修改；seekdb 实际存储工程资料并查询提供上下文；PowerContext 实际保存与恢复进度，恢复结果直接影响待办和后续上下文。这三项分别有独立原始记录。模型中间推理、认证信息不属于交付内容。

**有效修改的证据**：同一目标测试在原始实现上因边界断言失败，在 MiniMax 输出代码上通过；原有回归两次均通过，测试 SHA-256 不变。上下文来源清单与模型请求绑定，交付代码与模型最终回答绑定。规格更新后的上下文必须包含新规格，同时使上次验证失效。此实现不以界面、代码量或调用次数替代六项验收条件。
